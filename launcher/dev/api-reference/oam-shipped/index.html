Shipped Definitions

The component definitions and models that launcher ships inside the kurel binary (go-kure/launcher#1735). kurel build registers them before it reads an application’s own definitions/ and models/, so an application authors a shipped type with no file of its own.

set, err := shipped.Load(transformer) // registers the embedded set; refuses a file that does not load
err = set.Clash(h.TypeName(), h.Identity()) // refuses an application's type that is shipped

An application authors a shipped model by its identity, with no models/ directory (examples/s3-access, examples/workload-model).

Where it lives and how it loads

content/definitions/*.yaml are ComponentDefinition documents, and the CRD each pins sits in content/definitions/crds/, one YAML document per file. content/models/*.yaml are Model documents. Definitions load first, then models, each in file name order, so a shipped model may name a shipped definition’s type. The files load through the same loaders as an application’s own, so a CRD whose SHA-256 differs from its definition’s pin refuses the load, and a refusal names the file. A missing content/models directory holds no model. A shipped model registers with Registry.RegisterLazy: its expressions compile at the first build that uses it, not at every load, because every kurel build loads this set and compiling one model cost about 4 ms in a loaded process and about 22 ms more in a fresh kurel build (measured on one host, go-kure/launcher#1748). A test compiles each embedded model, so a model that does not compile fails CI, and a first use that finds one names the shipped file. A shipped model’s file is also decoded once for the process, because a decoded model is read-only.

A shipped type is never replaced

Set.Clash refuses an application’s definition that has the same authored type name as a shipped definition, an application’s model whose short name is one, and either that has the same identity as a shipped definition or model. The refusal names the type and the shipped file, and kurel build adds the application’s file. Another version of a shipped kind is another type and is not a clash. There is no override.

The s3-access model

s3-access.launcher.gokure.dev@v1 (go-kure/launcher#1738) says how to reach an S3 bucket, whatever S3 is behind it: a ConfigMap of the settings and, by the credentials route, the credentials in the keys a consumer reads. It creates no bucket (that is backend specific) and mounts nothing. A component of its type takes these inputs:

InputTypeDefaultMeaning
endpointstringrequiredThe endpoint URL, for example https://s3.example:9000
regionstringus-east-1
bucketstringrequired
prefixstring""A path inside the bucket
pathStylebooleantruePath-style addressing, because a custom endpoint rarely has wildcard DNS
caSecret{name, key}noneA Secret that holds the endpoint’s CA; key defaults to ca.crt. Only named in the ConfigMap
credentialsobjectrequiredExactly one of the three routes below

Credentials routes. credentials holds exactly one of these:

RouteWritesUnder a policy that forbids explicit secrets
existingSecret: <name>the ConfigMap only; the credentials stay in the Secret you madeallowed
externalSecret: {storeRef, accessKeyId, secretAccessKey, format, resticPassword, keys}the ConfigMap and an ExternalSecret whose template gives the keys of the format. storeRef is {name, kind} (kind defaults to ClusterSecretStore); each credential is a remote reference {key, property}allowed
values: {accessKeyId, secretAccessKey, format, resticPassword, keys}the ConfigMap and a Secret holding the valuesrefused with class RefusalExplicitSecret (the secret kind’s refusal)

format names the keys the credentials take. It defaults to plain. It is an input of values and of externalSecret only, never of existingSecret: the model cannot re-key a Secret it did not write (whether the External Secrets Operator could do it is not confirmed), so a format beside existingSecret is refused as an unknown field, not ignored. The design page proposed a top-level format; it sits inside the two routes so that it cannot be set where it does nothing.

formatKeys writtenSource
plainaccess-key-id, secret-access-key, endpoint, bucket-namethe model’s own names, the first two as both Garage operators write them
aws-envAWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_REGION, AWS_ENDPOINT_URL_S3the AWS SDK reference guide. AWS_ENDPOINT_URL_S3 is derived from the AWS_ENDPOINT_URL_<SERVICE> pattern, not printed there
credentials-fileone key, credentials, holding an AWS shared credentials file ([default], aws_access_key_id, aws_secret_access_key)the AWS SDK reference guide, shared credentials file
resticRESTIC_REPOSITORY (s3:<endpoint>/<bucket>[/<prefix>]), RESTIC_PASSWORD, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEYthe VolSync restic documentation, for the volsync trait’s repository Secret
barmanACCESS_KEY_ID, ACCESS_SECRET_KEYthe Barman Cloud plugin’s object store page, for a cnpg-objectstore’s s3Credentials
customthe two key names you give in keys (accessKeyId, secretAccessKey)none

resticPassword is required when format is restic: it is the repository’s encryption password and not an S3 setting, but VolSync reads it from the same Secret, which you cannot add a key to. On the values route it is a string; on the externalSecret route a remote reference. keys is required when format is custom.

The ConfigMap <component>-settings always holds endpoint, region, bucket-name, prefix, path-style (true or false), ca-secret-name, ca-secret-key (both empty without caSecret) and credentials-secret, the name of the Secret to read: yours, the one the model writes, or the one the ExternalSecret creates (it takes the ExternalSecret’s name). The model publishes the ConfigMap’s name as its output settings.

Not shipped: a session token; the Velero credentials format (not confirmed); a bucket; a mount of the CA. A nested input’s schema default is not applied by the loader, so the model reads an absent format as plain itself.

The workload model

content/models/workload.yaml is one model of type workload.launcher.gokure.dev@v1 (go-kure/launcher#1737), written type: workload@v1 in an application. A launcher-domain name takes a v<semver> version, which v1 is (pkg/oam/typeid.go). An application needs no models/ directory for it.

components:
  - name: orders
    type: workload@v1
    properties:
      image: registry.example.org/orders:1.0.0
      port: 8080
      volume: {size: 1Gi, mountPath: /data}
      monitoring: {path: /metrics}
InputType and defaultWhat it does
modeservice (default), worker or jobPicks the workload: webservice (Deployment, Service, ServiceAccount), worker (Deployment, ServiceAccount) or job (a Job, restartPolicy: OnFailure). Another word is refused.
imagestring, requiredThe container image, in every mode.
command, argslists of stringsThe container’s command and arguments.
envlist of {name, value, valueFrom{secretKeyRef, configMapKeyRef}}The container’s environment. With database set, DATABASE_URI is added from the uri key of the database’s application Secret.
replicasinteger, 1service and worker.
portinteger, 8080service: the container port and the Service port.
volume{size, mountPath, backup{schedule, repository}}Writes a claim named <component>-data and mounts it at mountPath in every mode. backup adds a volsync ReplicationSource for the claim; repository is the name of the restic Secret, which is referenced and never built.
exposure{hostnames}service only. Carries the expose trait on the Service, so the ClusterProfile’s expose capability picks an Ingress or an HTTPRoute.
database{storageSize, backup}Writes a postgresql component. backup has the shape of that component’s backup property (an S3 objectStore, retentionPolicy, schedules) and writes its object store and one ScheduledBackup for each schedule.
monitoring{port, path, interval, rules, scrapeName, ruleName}The property shape of the monitoring trait. Writes a VMServiceScrape in service mode, a VMPodScrape in worker and job mode, and a VMRule when rules is set.

Each optional input is a part of the model that is emitted only when the input is set; a build with image alone writes the workload and nothing else. port of monitoring is a port name or a number: in service mode it defaults to the Service’s http port, a number is written as targetPort, which names a port of the pod, and the model declares only port on the pod, so use the number of port (the build does not check it); in worker and job mode it is required and is a number, written as portNumber: the model writes no container port in those modes, so a port name would name nothing.

What the model format cannot express, and what the model does instead.

  • A trait cannot be conditional. The volume backup is the volsync trait on a part of its own, a serviceaccount that exists to carry it, so a volume backup writes one extra ServiceAccount, <component>-backup. The expose trait must sit on the component that owns the Service, so the service mode has two parts with one property list, one with the trait and one without.
  • A part’s type cannot depend on an input, so each mode is a part, and a read of a part’s outputs repeats that part’s condition. The DATABASE_URI environment entry is written in each of the workload parts, because a model value cannot read a part.
  • An input object must declare every key it takes. env, monitoring.rules and database.backup declare theirs, and a key they do not declare is refused.
  • A null is written to a generic-route object, and the CRD refuses it. So path and interval are written as /metrics and 30s when unset. The monitoring trait leaves both out and lets VictoriaMetrics’ defaults apply.
  • A part is named <component>-<part name>, and objectName is refused on it. So scrapeName and ruleName are the suffix of the object name (defaults <component>-scrape and <component>-rules), where the trait uses them as the whole name.
  • A model cannot refuse an input combination. exposure and port are read in service mode only and are not read in another. monitoring.port is required in worker and job mode; without it the build fails with no such key: port and names the part.
  • The scrape selects the app label of the workload by the name of its Deployment (the Job’s name in job mode). A Naming hook that renames the Deployment and not the label breaks the match.

Not covered. Probes, resources, a security context, sidecars and scaling are not inputs; the monitoring objects are held to the object kind policy as the trait’s are, so a policy that does not allow cluster-scoped objects refuses them (go-kure/launcher#1744). Restarting the workload when a config changes stays Go. There is no model per mode.

Where the CRDs come from

A CRD is taken from a release asset, never a branch. The three files are documents of https://github.com/VictoriaMetrics/operator/releases/download/v0.76.0/crd.yaml (6101924 bytes, sha256 9362fcf82df73584aa6d97651090be324475345e8e48495eedf810557f00af84, the digest the release lists), split with yq 4.54.3:

yq eval 'select(.metadata.name == "vmrules.operator.victoriametrics.com")' crd.yaml > content/definitions/crds/vmrules.yaml

The same command, with vmpodscrapes and vmservicescrapes, makes the other two. Each definition pins its split file’s digest. To move to another release, download that release’s crd.yaml, split the three files again and put the new digests in the definitions.

Only a CRD the loader accepts can ship. It refuses one whose spec is open (VMAuth and two other kinds), so the instance kinds are not shipped.

Not done

  • The CRDs’ CEL rules are not evaluated (see Component definitions).
  • The whole set registers on every build, used or not.
