OAM Model

Package oam is launcher’s core: the OAM data model, YAML parser, semantic validator, and the transform pipeline that turns an Application + ClusterProfile into Kubernetes manifests. Every document this package parses uses apiVersion: launcher.gokure.dev/v1alpha1 (SupportedAPIVersion); the one exception is the raw-document lowering seam, where a RawDocumentLoweringRule may claim a kind under a consumer-owned group via RawDocumentAPIVersioner (see Lowering).

Document kinds

KindTypePurpose
ApplicationApplicationThe app: components[] (each with type + properties) and traits[].
PackagePackageA package’s kurel.yaml descriptor: the declarations of its build-time parameters (ParameterDecl). The application is the separate app.yaml.
ClusterProfileClusterProfilePlatform choices (trait implementations, capabilities) supplied at build time, and the cluster’s Kubernetes release and per-gate feature-gate overrides (spec.kubernetesVersion, spec.featureGates; a library caller passes the overrides to ValidateAuthoredPropertiesForTargetWithGates and TransformContext.FeatureGates, see Property schemas and contract metadata).
CapabilityDefinitionCapabilityDefinitionDeclares the schema of a capability’s rendering: the keys a ClusterProfile binding for it may hold.

Component label and ownership

Every application of a transformed document belongs to one authored component, or to the document as a whole (go-kure/launcher#788). The transform records that as its last step, and two things follow from it: each application reports its owner, and each object it generates carries the owner’s component label.

Full text: Component label and ownership.

Reserved metadata keys

A consumer that keeps label and annotation keys to itself names them in TransformContext.ReservedMetadataKeys (go-kure/launcher#790). One rule holds every application the transform returns to the list, whatever wrote the key: a kind component, a passthrough or manifests object, a chart rendered at build time, a trait’s annotations, a postgresql or cnpg-cluster component’s inheritedMetadata.

Outputs: the names a component’s objects get

A consumer that wants to refer to an object a component generates (a Secret an operator reads, a Service a route points at) needs the object’s name before the document is built. A component type answers with the optional OutputProvider interface, which the ComponentLoweringRule claiming the type implements, or the handler when no rule claims it, as for EndpointProvider. Transformer.ComponentOutputs(comp) returns one Output per declaration, in the provider’s order: a Key, the object’s Kind (a schema.GroupKind) and its Name. A key is one identifier (a letter or underscore, then letters, digits and underscores), so a document can address it as parts.<part>.<key>. A type that provides no outputs answers (nil, nil).

Lowering

Some documents, components, traits, and policies are authored in a higher-level vocabulary that has no direct dispatchable handler — a type a platform wants expanded into one or more terminal types before the transform’s own component/trait dispatch runs. Where a component lowering rule places each object it emits (a same-name sibling member, a trait on one member, or a separately named kind component), and how a trait builds the same object as its kind twin, is set out in docs/oam/design-lowering-engine.md, section “Where a lowering rule places each object”.

After each lowering round, the engine resolves the types that a rule emitted. A type written as a declared identity becomes the registered name. A plain name that a handler or a rule is registered under stays as written, so a rule that emits plain names changes nothing. Where emission validation runs and the registered name declares a schema, the properties of an emitted component, trait or policy are checked against that schema, also when the rule wrote the type as an identity. The same holds for the platform-reserved check and for the members of a same-name sibling group. A rule reads the Naming hook of the run through LoweringContext.NamingHook. Transformer.CheckComponentTypes is a dry run of DeclareComponentTypes. It checks that the declaration is valid and declares nothing. It does not need the handler or rule to be registered yet, and DeclareComponentTypes does. A component model registers its rule only after this check passes (see Component Models).

Property schemas

Handlers may implement PropertySchemaProvider (PropertySchema() map[string]PropertySchema) to declare a constrained schema for their user-facing properties. PropertySchema is launcher’s single schema vocabulary — the same type also backs kurel.yaml parameters (ParameterDecl) and CapabilityDefinition rendering properties. It has Type (string/integer/boolean/number/array/object), Types, Description, Required, Default, Enum, nested Properties, Items, AdditionalProperties (default false; escape-hatch fields set it true), and Exclusive. The rich fields (Types, Enum, Properties, Items, AdditionalProperties, Exclusive) are meaningful only for handler properties: the two flat call sites (kurel parameters, capability rendering) reject them at decode time, so unifying the type does not widen their accepted behavior.
