Contributing

Launcher turns an application document into plain Kubernetes manifests. You use it as the kurel command line tool or as a Go library (pkg/oam). This section is for people who change it. Pick the route that matches your task.

Build, run and test

The Development Guide covers setup, the build, the test suite and the pre-commit checks. It also explains how a change reaches main. Releasing describes how a release is cut. The CI jobs are in GitHub Workflows and Shared Workflows.

Find your way around the code

Read the architecture map first. It lists every package under pkg/ and cmd/ with what it owns, shows how data moves through kurel build, and names the rules the code keeps and where each is enforced. It also says which five files to read first.

For the details of one stage of the pipeline, use the OAM reference. For the public API of one package, use the API reference.

Extend launcher

You want to addStart here
A component typeAdding a kind component and Extending
A traitThe Extending section of the traits package
A policyThe policies package: how a handler is registered and what it records
A probe row for the fill reportThe probe package: the checks name what a new fill needs

A new built-in is added in its handler package and in the map in pkg/oam/builtin/registry. A new terminal component type is also listed in validComponentTypes in pkg/oam/validate.go, or validation rejects it. A test pins the set of built-ins, so adding one is a visible change. The Adding a kind component page has the full checklist.

Keep the documents in step

A change to a package updates that package’s README.md and any page that describes it, in the same pull request. A change that adds a package under pkg/ or cmd/ also adds a row to the map in ARCHITECTURE.md; a test fails until it does.
