Compatibility Matrix

Kure Compatibility Matrix

This document describes the versions of infrastructure tools that Kure supports. It is generated from versions.yaml (deployment compatibility metadata) plus go.mod (the build versions).

Version Philosophy

Kure maintains two version concepts for each dependency:

  1. Build Version (read from go.mod): The exact library version Kure imports and builds against
  2. Deployment Compatibility (supported_range in versions.yaml): The range of deployed tool versions that Kure can generate YAML for

Consumers that need the deployment-compatibility metadata (2) or the Go toolchain version programmatically should import github.com/go-kure/kure/pkg/versions rather than parsing versions.yaml. Per-dependency build versions (1) are not exported – they change on every routine bump, so keeping them out keeps this API’s content stable; read them from go.mod instead.

gateway-api1.7.01.0 - 1.7Gateway API v1 types (HTTPRoute). Used by pkg/kubernetes HTTPRoute builders. Kure generates gateway.networking.k8s.io/v1 resources (GA since v1.0). v1.6 is a routine minor with no changes to the imported gateway.networking.k8s.io/v1 HTTPRoute type — build + tests pass unchanged. v1.7 (from v1.6.3): kure imports apis/v1 only. kure’s generated YAML is unchanged and build + tests pass unchanged. kure’s HTTPRoute helpers (AddHTTPRouteHostname, AddHTTPRouteParentRef, AddHTTPRouteRule and the rule match, filter and backendRef helpers) append the caller’s value whole and set no field of their own, so every change below applies to an HTTPRoute built through them as to any other. Standard channel: HTTPRouteRule.Retry graduates from experimental. Retry semantics change: a request is retried when the backend did not process it, that is when the connection could not be established or the backend rejected it, either before processing it or with one of the configured status codes (codes 500, 502, 503 and 504 stay MUST support), and an implementation SHOULD NOT retry by default where the request may have been processed, such as a reset after it was sent (was SHOULD retry on disconnect, reset, timeout and TCP failure), documenting any such retry; HTTPRouteRetry.Attempts counts retries in addition to the first request, defaults to 1 and has minimum 0 (was minimum 1, unset meant implementation-specific; an explicit 0 disables retries); HTTPRouteRetry.Backoff becomes the base interval of the implementation’s backoff strategy (was a guaranteed minimum delay), its support level drops from Extended to Implementation-specific, and an implementation that retries with no backoff MUST NOT advertise support and MUST set Accepted False with reason UnsupportedValue on a route that sets it; an implementation MAY add jitter and MAY cap the delay at a maximum of its own, which SHOULD NOT be less than the base interval. Rule names must be unique within an HTTPRoute or GRPCRoute (was experimental-only validation). Hostname precedence: when routes on one listener yield identical intersected hostnames, an implementation SHOULD rank them by the hostnames written on each route, not the intersection (Extended feature GatewayRouteHostnameIntersectionPrecedence; one without it MAY use the intersection), on HTTPRoute, GRPCRoute and TLSRoute, and GRPCRoute and TLSRoute now state the most-specific-hostname rule HTTPRoute already had; when an HTTPRoute and a GRPCRoute share a listener hostname an implementation MAY reject one (was MUST). GatewayClass controllerName stays immutable through +k8s:immutable instead of a CEL rule. A policy targetRef sectionName on a ListenerSet names a listener. Experimental channel: SessionPersistence drops SessionName and CookieConfig for Cookie (CookieConfig gains Name and Path) and Header, so its wire keys move from sessionName/cookieConfig to cookie/header, and type Cookie or Header now requires its matching block and forbids the other, so a bare type Cookie no longer validates; the session name tightens: header.name is required and Core support, and cookie.name and header.name must be 1 to 256 RFC token characters (was an optional sessionName of at most 128 characters of any kind, so a name such as “session id” and an empty header block no longer validate); an implementation SHOULD generate a unique cookie name when cookie.name is unset, and cookie.path defaults to “/” (MUST), which sets the cookie scope even where a caller does not write it; cookie.name and cookie.path are Extended support (sessionName was Implementation-specific), which an implementation SHOULD support where its dataplane allows, and cookie.path is at most 1024 characters; HTTPRouteRule.SessionPersistence and GRPCRouteRule.SessionPersistence are deprecated for the Backend resource (GEP-4894); ForwardBodyConfig.MaxSize, inside the ExternalAuth filter, is retyped from uint16 to int32 with minimum 0; BackendTLSPolicy and Gateway frontend TLS CA references accept a ClusterTrustBundle (namespace unset) at Extended support, and BackendTLSPolicy validation takes exactly one of caCertificateRefs and wellKnownCACertificates through ExactlyOneOf with caCertificateRefs MinItems 1 (the standard channel keeps the two CEL rules); a backend reference to an XBackend must not set a port; Listener filters are allowed only on HTTP and HTTPS listeners and apply only to HTTP or to HTTPS with TLS terminated at the Gateway; a listener takes at most 16 request filters, each with exactly one payload, the one its type (ExternalAuth or ExtensionRef) names; an implementation MUST run them in the order written or set Accepted False with reason InvalidListenerFilterOrder, MUST NOT let them change the Host or :authority header (it SHOULD ignore such a change and continue, or MAY fail the request with a 5xx), MUST match routes exactly once after the last filter, and MUST NOT re-select the listener; a Routability value must be empty, Cluster or a domain-prefixed implementation-specific value of at most 253 characters, with k8s.io and its subdomains reserved; empty or unset uses the implementation’s default, Cluster means a Kubernetes Service ClusterIP, and a requested Routability on GatewaySpecAddress is Extended support. Additive: Filters on Listener and ListenerEntry (ExternalAuth, ExtensionRef), Routability on GatewaySpecAddress and GatewayStatusAddress, and the AddressesAssigned Gateway condition with its reasons. A caller assigning a removed or retyped field fails to compile; an object relying on a dropped behaviour (duplicate rule names, unset retry attempts, retry on reset or a guaranteed backoff minimum, the v1.6 session persistence shape) needs rework against the v1.7 CRDs and the implementation’s documented retry behaviour.

Understanding the Matrix

Build Version (go.mod)

The version Kure imports and builds against — read directly from go.mod, the single source of truth for the pin. CI (sync-versions.sh check) asserts it falls within the declared supported_range — except an entry whose Deployment Compatibility cell reads “derived from <module>” (an MVS-floor dependency): its pin is not chosen by Kure, so there is no independent range to assert, and CI instead only checks that the pin matches what <module>’s own go.mod requires. See docs/dependency-updates.md’s “MVS-floor dependencies” section.

Deployment Compatibility

The range of versions that Kure can generate valid YAML for. Kure may generate YAML compatible with older or newer versions than it builds against.

For example, Kure may build against a single cert-manager patch release while the generated YAML stays valid across several older and newer minor releases within its supported range.

Upgrading Dependencies

When upgrading a dependency:

  1. Run go get <module>@<version> to update go.mod
  2. Update code for any API changes
  3. If the new version lands outside supported_range, widen the range and update notes in versions.yaml (only after confirming API compatibility). In-range patch bumps need no versions.yaml change.
  4. Run ./scripts/sync-versions.sh generate to update docs
  5. Run ./scripts/sync-versions.sh check to validate consistency
